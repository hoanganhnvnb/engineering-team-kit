# Git

How to write commits, name branches and tag releases.

## Commit style: who decides

1. Commit tooling (commitlint, commitizen, gitmoji config, `commit-msg` hook) or a format
   stated in project docs (CLAUDE.md, CONTRIBUTING) decides.
2. Else the workflow profile's `commit.style`/`commit.language`.
3. Else, if ≥70% of the last 20 non-merge subjects (`git log -20 --no-merges --format=%s`) share a style, follow it.
4. Else Conventional Commits 1.0.0: `type(scope): description`.

## Types

- `feat`: a new user-facing feature.
- `fix`: a bug fix.
- `docs`: documentation only.
- `style`: formatting, whitespace; no behavior change.
- `refactor`: code change that neither fixes a bug nor adds a feature.
- `perf`: a performance improvement.
- `test`: add or fix tests.
- `build`: build system, packaging or dependencies.
- `ci`: CI configuration and scripts.
- `chore`: maintenance that touches no source or tests.
- `revert`: revert an earlier commit; name it in the body.

## Message

- Type and scope are always English. Scope: one already used in history, else the
  package or top-level module, kebab-case. Omit scope if the change spans > 2 areas.
- Description in English unless the history is mostly another language. Imperative
  mood, lowercase start, no trailing period. Whole subject <= 72 chars.
- Body explains why, not what; wrap at 72.
- Breaking change: `!` after type/scope, plus a `BREAKING CHANGE: <what to do>` footer
  explaining the migration (the spec accepts either; use both).
- Reference tickets in the footer (`Refs: ABC-123`) or the way the project does.
- No AI/assistant co-author or "generated by" trailers.

## Commits

- One logical change per commit. Stage files by name; never `git add -A` or
  `git add .` in a user's checkout.
- Never commit secrets, generated files or unrelated edits.
- Never use `--no-verify`, never force-push, never rewrite published history.

## Branches and tags

- Branch: the workflow profile's `branches.name_pattern` if set; else the pattern existing branches use;
  else `<type>/<ticket>-<slug>` (drop `<ticket>-` when there is none), kebab-case, e.g. `fix/ABC-123-null-cart-total`.
- Tag releases `vX.Y.Z`, annotated (`git tag -a`), on the release commit.

## Examples

- Good: `fix(cart): keep discount when currency changes`
- Bad: `Fixed bug.` (no type, past tense, vague, trailing period)
- Good: `feat(api)!: require auth on /v1/orders` + footer `BREAKING CHANGE: send a token`
- Bad: `chore: update stuff and fix login and add tests` (three changes, wrong type)
